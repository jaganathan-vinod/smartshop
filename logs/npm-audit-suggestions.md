## Safer alternatives if a force upgrade would break CDK or React Router v6

### If you want to avoid **React Router 7** for now

1. **Compensating controls (stay on v6 temporarily)**  
   - Centralize navigation helpers: only allow paths matching `^/[a-zA-Z0-9/._-]*$` (no `\`, no `//`, no scheme).  
   - Sanitize **`location.state.from.pathname`** before `navigate(state.from.pathname)` (login redirect).  
   - Keep `to`/`navigate` on **literals or server-known IDs**, not raw query/reflected URL parameters.  
   - Re-run audit after controls; advisories remain until **≥7.18.0**, but exploitability drops sharply for a static-route SPA.

2. **Incremental path to v7 (less “big bang” than `--force`)**  
   - Follow [React Router upgrading guide](https://reactrouter.com/upgrading/v6) (v7 can run with v6-style APIs in many apps).  
   - Upgrade **`react-router-dom@7.18.4`**, fix breaking changes in `web/src/App.tsx` / route modules, run `web` tests and smoke auth/checkout flows.  
   - Avoid `npm audit fix --force` without a migration branch and test plan.

3. **SSR advisory**  
   - No change required for GHSA-337j-9hxr-rhxg beyond upgrading when you move to RR7 — you do not use SSR hydration today.

### If you want to avoid **esbuild 0.28** breaking CDK

1. **Minimal semver bump:** set `infra` `esbuild` to **`^0.25.0`** or **`^0.27.0`** first (still fixes `<=0.24.2`). Only go to **`^0.28.2`** if synth/tests pass and you want parity with audit’s suggested fix.

2. **Risk acceptance (documented):** keep 0.24.x only if you explicitly accept **dev-server** CVE with controls: never run esbuild’s `serve` on `0.0.0.0`, never expose bundler ports in CI previews. This does **not** remove npm audit noise but matches actual CDK usage.

3. **Do not** downgrade CDK to “fix” esbuild — CDK already expects modern esbuild; aligning **infra’s direct `esbuild`** with what `aws-cdk-lib` lambda-nodejs uses (via lockfile) is the usual approach.
